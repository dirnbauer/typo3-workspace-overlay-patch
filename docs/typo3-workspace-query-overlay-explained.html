Non-Technical Summary

TYPO3 workspaces let editors prepare content changes without publishing them immediately. The live website keeps showing the old content, while editors in the workspace should see and manage the draft content.

The problem was that some backend views searched in the live content first and only applied the workspace draft afterwards. If a title, page type, slug, or label existed only in the draft version, TYPO3 could miss it or show the wrong row state.

In simple terms: editors could create a correct draft, but parts of the backend could still search, count, or display it as if the old live version was the only version.

This matters because workspace users need to trust the backend. Search results, record lists, icons, slugs, and publish decisions must reflect the draft they are reviewing, not stale live data. Otherwise editors can overlook changes, duplicate values, publish the wrong assumption, or waste time checking whether TYPO3 or their content is wrong.

The patch makes those backend queries look at the relevant draft rows first and then normalize the result so TYPO3 still behaves like one logical record. Normal live-mode behavior stays unchanged.

Short Version

TYPO3 workspace overlay is a two-step process:

1. Query records TYPO3 fetches database rows with Doctrine QueryBuilder and restrictions.
2. Overlay records TYPO3 replaces live rows with workspace rows using workspaceOL() or versionOL().

The bug happens when step 1 filters by a field that only has the new value in the workspace row. The workspace row is excluded too early, so step 2 never gets a chance to overlay it.

The patch lets selected backend queries fetch all workspace rows first, then overlay and reduce them back to the expected live uid. This fixes search/list/suggest/slug cases without changing normal live queries.

Workspace Basics

Workspace versions live in the same table as live records. TYPO3 does not store drafts in a separate table. Instead, the versioning fields decide what a row means.

Field Meaning
uid The database row id. Workspace rows have their own uid.
t3ver_oid For a workspace version of an existing record, this points to the live record uid.
t3ver_wsid The workspace id. Live rows use 0.
t3ver_state Special workspace state: normal version, new placeholder, delete placeholder, move pointer.

Example Data

-- Live row
uid = 1
t3ver_oid = 0
t3ver_wsid = 0
header = "Live title"

-- Workspace row in workspace 1
uid = 42
t3ver_oid = 1
t3ver_wsid = 1
header = "Draft title"

After overlay, TYPO3 normally wants the result to behave like this: 

uid = 1
_ORIG_uid = 42
header = "Draft title"

Preserving the live uid is important. TYPO3 references, links, permissions, and UI state often expect the record identity to stay the live uid, while the field values come from the workspace row.

Moving A Record Twice

Short answer for an existing live record in one workspace: TYPO3 normally creates only one workspace row for that logical record. If the editor moves the record a second time, TYPO3 updates the same workspace row. It does not create a second move-pointer row, and it does not build a pointer chain.

A move pointer is not a history entry for one move operation. It is the current workspace-position marker for one live record. Its t3ver_oid stays the live record uid.

What TYPO3 Does

Action What happens in the database
First move in a workspace TYPO3 creates or reuses one workspace row and marks it as t3ver_state = 4. This row stores the draft location with its pid and sorting fields.
Second move of the same record in the same workspace TYPO3 updates the same workspace row. The pid and sorting fields change to the latest target position.
Pointer target t3ver_oid keeps pointing to the original live record uid, for example t3ver_oid = 89.

What TYPO3 Does Not Do

Not done Why it matters
No second move-pointer row for the same live record The second move overwrites the draft position on the existing workspace row.
No pointer chain The second move does not create second move -> first move -> live record. TYPO3 keeps workspace row -> live record.
No live move yet The live row is not moved while editing in the workspace. The move becomes live only when the workspace change is published.
No full move history in the record table The workspace row stores the latest draft position, not every intermediate position. Move history can be logged elsewhere, but not as a chain of t3ver_state = 4 rows.

Existing Live Record Moved Once

Suppose the live page record is this: 

uid = 89
pid = 88
t3ver_wsid = 0
t3ver_oid = 0
t3ver_state = 0
title = "Relations"

In workspace 1, moving it creates one extra row: 

uid = 92
pid = 90                 -- target location in the workspace
t3ver_wsid = 1
t3ver_oid = 89           -- points to the live/original uid
t3ver_state = 4          -- MOVE_POINTER
title = "Relations"

The important part is t3ver_oid = 89. The workspace row is not the canonical identity. It is a workspace overlay for live record 89.

Same Record Moved Again

If the editor moves the same record again in the same workspace, TYPO3 does not create another row like uid = 93 pointing to uid = 92. Instead, it updates the existing row: 

uid = 92
pid = 1                  -- latest target location
sorting = 128            -- latest sorting position
t3ver_wsid = 1
t3ver_oid = 89           -- still points to the live/original uid
t3ver_state = 4          -- still MOVE_POINTER
title = "Relations"

So the database shape is: 

live row 89
  ^
  |
workspace move pointer row 92

Not this: 

live row 89 <- first move row 92 <- second move row 93

Why TYPO3 Reuses The Same Row

DataHandler::moveRecord() first checks whether the live record already has a workspace overlay in the current workspace. The lookup is done by live uid: 

BackendUtility::getWorkspaceVersionOfRecord($workspaceId, $table, $liveUid)

That lookup searches for a row where: 

t3ver_wsid = current workspace
AND t3ver_oid = live uid

If such a row exists, TYPO3 uses that row as the $workspaceRecord. Later in the move, TYPO3 updates pid and sorting fields on that row: 

UPDATE table
SET pid = latest target pid,
    sorting = latest sorting value
WHERE uid = workspace row uid

If the existing workspace row was a normal changed row with t3ver_state = 0, moving it turns that same row into t3ver_state = 4. If it was already a move pointer, it remains a move pointer and only the position changes.

Workspace-New Records Are Different

A record created only inside a workspace has no live original yet. It uses: 

t3ver_oid = 0
t3ver_state = 1          -- NEW_PLACEHOLDER

If that workspace-new record is moved twice before publishing, TYPO3 still updates the same row. It usually stays a new placeholder because there is no live uid for a move pointer to point to.

Translations And Child Records

Moving one default-language page can also move related localization rows or inline child records. In that case you may see more than one workspace row in total, but each row belongs to its own live record. 

live default page 89
  ^
  |
workspace move row 92, t3ver_oid = 89

live translated page 91
  ^
  |
workspace move row 93, t3ver_oid = 91

This is not a chain. It is one workspace row per affected live record.

If a table contains two move-pointer rows in the same workspace with the same t3ver_oid, that is not the normal DataHandler result. It is a broken or manually created state, and overlay code may return whichever matching row the database returns first.

The Actual Bug

The default WorkspaceRestriction is conservative. In a workspace it usually returns: 

live rows
+ workspace-new rows
+ move pointers

It does not include normal changed workspace rows for existing records. That is fine when querying by uid or pid and overlaying afterwards. It breaks when the SQL query filters by a field that was changed only in the workspace.

Broken Search Example

WHERE header LIKE "%Draft title%"

The live row has header = "Live title", so it does not match. The workspace row has header = "Draft title", but the default workspace restriction excludes it because it is a normal version row with t3ver_oid > 0.

Result: no row is returned. The overlay code is not wrong in this case. It simply never sees the row.

Relation To Forge Issue 109577

Forge issue 109577 fixed an ordering problem in the record list: overlay had to happen before creating resolved record objects. This patch addresses the next layer of the same family of problems: the query must not filter out the workspace row before overlay can run.

The Generic Fix

The patch does three things.

1. Better Query API

Adds QueryBuilder::addWorkspaceRestriction() so code can clearly say: 

$queryBuilder->addWorkspaceRestriction(
    $workspaceId,
    $includeAllVersionedRecords
);

2. Central Decision Helper

Adds WorkspaceRestriction::shouldIncludeAllVersionedRecordsForBackendQuery(). This avoids every backend class inventing its own workspace switch logic.

3. Overlay Direct Workspace Rows

Updates workspaceOL() and versionOL() so they also handle rows that are already workspace rows, not only live rows.

The Switch

The include-all behavior is enabled only in backend workspace context. It can be disabled with User TSconfig: 

options.workspaces.includeAllVersionedRecordsInQueries = 0

The helper returns true only when all of this is true:

Condition Why
EXT:workspaces is loaded No workspace logic when the extension is unavailable.
$GLOBALS['BE_USER'] exists This is backend behavior, not a generic frontend default.
Backend user workspace is not 0 Live workspace must keep the old fast path.
TSconfig does not disable it Site owners can turn it off if they hit a performance or compatibility problem.

The Gate (Single On/Off Switch)

"The gate" is one static helper method, called from every patched location in the exact same if form: 

if (\TYPO3\CMS\Core\Database\Query\Restriction\WorkspaceRestriction::shouldIncludeAllVersionedRecordsForBackendQuery()) {
    // ... patched behavior
}

Defined in vendor/typo3/cms-core/Classes/Database/Query/Restriction/WorkspaceRestriction.php, it returns true only when all four conditions hold:

# Condition Returns false when
1 EXT:workspaces is loaded The workspaces extension is missing.
2 $GLOBALS['BE_USER'] is a real BackendUserAuthentication No backend session (frontend, CLI, anonymous).
3 Backend user workspace is not 0 The user is currently in the live workspace.
4 TSconfig options.workspaces.includeAllVersionedRecordsInQueries is not 0 (defaults to 1) The site or user has explicitly disabled the patch.

Where The Gate Is Used

Seven call sites, one helper, one TSconfig key. The gate now wraps both halves of the patch (queries and overlays):

Half File What it gates
Query (broaden search results) typo3/cms-backend/Classes/RecordList/DatabaseRecordList.php Record-list search restriction (only when searchString !== '').
typo3/cms-backend/Classes/Search/LiveSearch/DatabaseRecordProvider.php Live-search record restriction.
typo3/cms-backend/Classes/Search/LiveSearch/PageRecordProvider.php Live-search page restriction.
typo3/cms-backend/Classes/Form/Wizard/SuggestWizardDefaultReceiver.php Suggest-wizard restriction.
typo3/cms-core/Classes/DataHandling/SlugHelper.php Slug-uniqueness restriction.
Overlay (normalize direct workspace rows) typo3/cms-backend/Classes/Utility/BackendUtility.php workspaceOL() uid-normalization block.
typo3/cms-core/Classes/Domain/Repository/PageRepository.php versionOL() uid-normalization block.

Why It Matters: Full On/Off Toggle

Earlier the gate covered only the five query call sites. The two overlay normalizers always ran, so disabling the TSconfig left the patch half-active: a workspace row that reached workspaceOL()/versionOL() by any path still had its uid normalized to the live oid. That mismatched the search side and could surface a normalized live uid for a soft-deleted live row, which then crashed callers like ElementInformationController.

Wrapping the overlay normalizers in the same gate makes the patch a single binary:

options.workspaces.includeAllVersionedRecordsInQueries Search broadens? Overlay normalizes direct workspace rows?
1 or unset (default) yes yes
0 no (vanilla WorkspaceRestriction) no (falls through to original core logic)

Live Verification

The toggle was confirmed end-to-end against a real workspace row (tt_content/12701, a workspace VERSION whose live uid=12485 was soft-deleted):

Call Switch ON Switch OFF
getRecordWSOL('tt_content', 12701) uid=12485, _ORIG_uid=12701 (normalized) uid=12701, _ORIG_uid=- (untouched)
getRecordWSOL('pages', 705) (move pointer) uid=686, _ORIG_uid=705 (normalized) uid=705, _ORIG_uid=- (untouched)

How To Flip It

Sitewide via page TSconfig (e.g. Configuration/page.tsconfig in a sitepackage): 

options.workspaces.includeAllVersionedRecordsInQueries = 0

Per user or group via the TSconfig field in the BE user/group module.

Because the gate also requires $GLOBALS['BE_USER'] and a non-live workspace, the patch is automatically dormant for anonymous frontend requests, CLI commands, and admins working in the live workspace. There is no separate frontend kill-switch needed.

File By File

coreClasses/Database/Query/QueryBuilder.php

Adds a small developer-experience helper: 

public function addWorkspaceRestriction(
    int $workspaceId,
    bool $includeAllVersionedRecords = false
): self {
    $this->restrictionContainer
        ->removeByType(WorkspaceRestriction::class)
        ->add(GeneralUtility::makeInstance(
            WorkspaceRestriction::class,
            $workspaceId,
            $includeAllVersionedRecords
        ));

    return $this;
}

Before this, callers had to manually remove/add restrictions. The helper makes the intent readable and reduces copy-paste bugs.

coreClasses/Database/Query/Restriction/WorkspaceRestriction.php

Adds the central backend decision helper: 

WorkspaceRestriction::shouldIncludeAllVersionedRecordsForBackendQuery()

This does not change the SQL by itself. It only answers the question: "Should this backend query include all version rows and reduce after overlay?"

coreClasses/Domain/Repository/PageRepository.php

PageRepository::versionOL() used to assume that the incoming row was usually a live row. With include-all queries, the incoming row can already be a workspace row.

The patch adds an early normalization block, wrapped in the central gate so the whole patch can be turned off with one TSconfig key. Defensive casts and null-coalesce keep it safe when the optional version fields are missing from the incoming row: 

if (WorkspaceRestriction::shouldIncludeAllVersionedRecordsForBackendQuery()) {
    $workspaceId = (int)$this->context->getPropertyFromAspect('workspace', 'id');
    $rowVersionState = VersionState::tryFrom($row['t3ver_state'] ?? 0);
    if ((int)($row['t3ver_wsid'] ?? 0) === $workspaceId) {
        if ($rowVersionState === VersionState::DELETE_PLACEHOLDER) {
            $row = false;
            return;
        }
        if ((int)($row['t3ver_oid'] ?? 0) > 0) {
            // For MOVE_POINTER also fill _ORIG_pid from the live row (omitted for brevity).
            $row['_ORIG_uid'] = $row['uid'];
            $row['uid'] = $row['t3ver_oid'];
            return;
        }
    }
}

In plain words: if we already have the draft row, keep its field values but make it look like the live uid again. The same outer t3ver_wsid branch also handles delete placeholders by removing the row from the result entirely. When the gate is off, the block is skipped and core falls through to its original logic.

coreClasses/DataHandling/SlugHelper.php

Slug uniqueness is part of create/update behavior. If a draft page already uses /workspace-only-slug, TYPO3 must not allow another record in the same workspace to accidentally reuse it.

The patch changes SlugHelper to use: 

$queryBuilder->addWorkspaceRestriction(
    $this->workspaceId,
    WorkspaceRestriction::shouldIncludeAllVersionedRecordsForBackendQuery()
);

SlugHelper already had overlay/reduce logic after fetching. The missing part was fetching the draft row in the first place.

backendClasses/Utility/BackendUtility.php

BackendUtility::workspaceOL() gets the same direct-workspace-row normalization as PageRepository::versionOL(), wrapped in the same gate: 

if (WorkspaceRestriction::shouldIncludeAllVersionedRecordsForBackendQuery()) {
    $versionState = VersionState::tryFrom($row['t3ver_state'] ?? 0);
    if ((int)($row['t3ver_wsid'] ?? 0) === $wsid) {
        // DELETE_PLACEHOLDER -> $row = false
        // t3ver_oid > 0      -> $row['uid'] = $row['t3ver_oid']; $row['_ORIG_uid'] = old uid
    }
}

This matters for backend modules like record list, suggest wizard, live search, recycler, and info views because many of them call BackendUtility::workspaceOL() after the query. Disabling the TSconfig key turns this normalization off in lockstep with the search broadening, so the patch cannot end up half-active.

backendClasses/RecordList/DatabaseRecordList.php

This is the main visible fix for "Records view search".

The patch:

Change Reason
Uses include-all workspace rows only when $this->searchString !== ''. Normal list views keep the faster old behavior.
Counts distinct live ids with a CASE WHEN t3ver_oid > 0 expression. Live row and draft row should count as one logical record.
Deduplicates rows after overlay by $record->getUid(). Include-all queries can return live and workspace rows for the same logical record.

backendLiveSearch providers

These files are patched:

  • Classes/Search/LiveSearch/DatabaseRecordProvider.php
  • Classes/Search/LiveSearch/PageRecordProvider.php

Live search already used include-all in one place. The patch keeps the behavior in workspace context, but routes it through the central switch so it can be disabled consistently.

backendClasses/Form/Wizard/SuggestWizardDefaultReceiver.php

Suggest wizard searches by labels and configured fields. Those are editable fields, so they can have draft-only values. The patch makes the suggest query use the same include-all rule.

How To Reproduce

Two one-time setup steps were required before the suite would run inside this distribution. Both are recorded so anyone can reproduce the live run:

  1. Project-level test scaffolding. A copy of TYPO3's functional-test configuration lives at Build/FunctionalTests.xml and Build/FunctionalTestsBootstrap.php. The bootstrap does two extra things on top of the vanilla testing-framework boilerplate:
    • Defines the TYPO3 constant before package discovery so that any extension's ext_emconf.php with a top-level defined('TYPO3') or die(); guard (this project has two such files in vendor/webconsulting/*) does not silently kill the bootstrap when ComposerPackageManager::getExtEmConf() includes it.
    • Registers a small PSR-4 autoloader that maps TYPO3\CMS\<Ext>\Tests\… to vendor/typo3/cms-<ext>/Tests/…, because the vendor packages ship their test trees outside the published composer autoload.
  2. Database grant. The testing-framework creates a fresh per-test database named db_*. The DDEV default user db only has access to db, so a one-shot grant is needed: 
    ddev exec mysql -uroot -proot -e "GRANT ALL ON \`db_%\`.* TO 'db'@'%'; FLUSH PRIVILEGES;"

With that in place, the five-test suite is reproducible from the project root: 

ddev exec env typo3DatabaseDriver=pdo_mysql typo3DatabaseHost=db \
    typo3DatabaseName=db typo3DatabaseUsername=db typo3DatabasePassword=db \
    vendor/bin/phpunit -c Build/FunctionalTests.xml \
    --filter queryBuilderCanAddWorkspaceRestrictionDirectly

Substitute the other four method names from the table above to run each test on its own. The whole suite takes roughly ten seconds on this machine.

The root composer.json contains the patch entries. patches.lock.json stores the calculated patch hashes. That means Composer can verify that the patch files did not silently change.

Mental Model

The safe rule for TYPO3 workspace-aware queries is:

If a query filters by fields that editors can change in a workspace, the query probably needs to include all workspace rows and then overlay/reduce afterwards.

Use Default Restriction When

  • You query by stable identifiers like uid or simple page position.
  • You do not search/filter by editable record fields.
  • You need the fastest normal list/tree path.

Use Include-All Restriction When

  • You search by title, header, slug, description, label, or other editable fields.
  • You already call workspaceOL(), versionOL(), or another reduce step after fetching.
  • You can deduplicate by live uid after overlay.

Practical PHP Pattern

$queryBuilder = $connectionPool->getQueryBuilderForTable($table);
$queryBuilder->getRestrictions()
    ->removeAll()
    ->add(GeneralUtility::makeInstance(DeletedRestriction::class));

$queryBuilder->addWorkspaceRestriction(
    $backendUser->workspace,
    WorkspaceRestriction::shouldIncludeAllVersionedRecordsForBackendQuery()
);

// Build WHERE on editable fields here.
// Fetch rows.
// Then call workspaceOL/versionOL and deduplicate by live uid.
